bbtree 是目前我所知最快的 B 树：

  1. 单线程下比 std 的 BTreeMap 快 5 倍，96 线程下比 crossbeam-skiplist 快 12 倍。
  2. 内存占用低 30%。
  3. 零依赖，兼容 no_std。
  4. bbtree::unsync::BBTreeMap 可以直接替换 std 的 BTreeMap/BTreeSet。
  5. 经过形式化验证、模型检查、确定性模拟、模糊测试和大量测试，已达到生产可用状态。
  6. 背后是数十年的数据库研究积累，以及 Xiangpeng Hao 的精心打磨。

它能做什么？

B 树是大数据系统中最重要的数据结构，一棵像 bbtree 这样快的 B 树，能让建立在它之上的一切受益：智能体内存、LLM 训练、RAG、KV 存储、状态缓存、向量搜索，等等。

这里讨论三个有代表性的用例：

  1. 替换 LSM 树中的跳表。 在四个 LSM 树中替换原有跳表后，bbtree 快 1.37–6.83 倍。
  2. 内存数据库索引。 替换 Turso 的跳表后，插入快 2.22 倍，带索引的 SELECT 快 1.90 倍。
  3. 从磁盘 mmap 一个 bbtree。 重启后无需重建：首个查询结果比 std 的 BTreeMap 早 160–2,500 倍返回。

所有 LSM 树都用一种有序映射在内存中保存最近的写入，也就是 memtable。在 Rust 中，这个有序映射通常是跳表，例如 crossbeam-skiplist。

bbtree 可以轻松替换它，而且快得多。跳表在下行过程中几乎每访问一个节点就会发生一次缓存未命中；而 bbtree 的一次查找只触碰少量缓存行（见下文“它是怎么做到的”）。

bbtree 的接口与 crossbeam-skiplist 类似，但更简单：没有 epoch，不必操心何时 pin 或重新进入 epoch。

bbtree 允许更高级的内存管理：

  1. 从一开始就支持自定义分配器。
  2. 它从不按不规则大小（即非 2 的幂）分配：内存管理保持简单，不会产生外部碎片[2]。
  3. 分配失败可以被优雅地处理。

我们把 bbtree 集成进四个 LSM 树，并在各系统自己的基准上测试：

  1. fjall：get 2.47 倍，insert 1.61 倍，写批次 3.00 倍。
  2. SlateDB：get 1.71 倍，put 1.65 倍，每批 10 行的写入 2.36 倍。
  3. Tonbo：1000 万行写入 6.83 倍，带冲突检查的事务 4.10 倍。
  4. Lance 的 MemWAL 索引（它自己的跳表）：点查 2.19 倍，批量查找 3.94 倍，批量写入 4.21 倍。
Next, 2 of 3Case 2: database index→

数据库的表在读取的同时也在变化：查询之间会有行被插入、更新和删除，表的每个索引也随之变化。内存数据库把每一张表放进一个有序映射，而这个映射必须在这些写入之下始终保持有序。

Turso 是用 Rust 重写的 SQLite，它把 MVCC 存储放在内存中：表的行和索引项各自保存在一个 crossbeam-skiplist 里。换成 bbtree 后，在 Turso 自己的基准上：

  1. 随机 rowid 的 INSERT：2.22 倍。
  2. 带索引的点查 SELECT：1.90 倍。
  3. BEGIN CONCURRENT 中的 UPDATE：1.22 倍。
  4. 按 rowid 的点查 SELECT：1.16 倍。
Next, 3 of 3Case 3: bbtree-mmap→

bbtree-mmap 允许你构建一次 bbtree 并写入磁盘；需要时直接 mmap 即可立即使用，无需重建。

cargo add bbtree-mmap

构建 bbtree 并保存到磁盘

use bbtree::unsync::BBTreeMap;
use bbtree_mmap::BBTreeMapFile;

let names = BBTreeMap::from([(7_u64, String::from("ferris")), (42, String::from("corro"))]);
BBTreeMapFile::<u64, String>::create("names.bbtree", &names)?;

mmap bbtree 并立即查询

use bbtree_mmap::BBTreeMapFile;

let names = unsafe { BBTreeMapFile::<u64, String>::mmap("names.bbtree").open()? };
assert_eq!(names.get(&42), Some("corro"));

它是怎么做到的？

每一个性能优化都应该由成本模型来指导。

B 树的优化很简单，只有三块拼图[3]：只需按顺序记住三条原则：

  1. 触碰的串联缓存行数量。一次缓存未命中大约花费 100 ns。
  2. 执行的指令数量。一条指令大约花费 0.5 ns。
  3. 缓存一致性流量的大小，这在并发访问时尤其重要。它会强制产生一次缓存未命中，代价略高于 100 ns。

有了这个成本模型，最重要的优化显然是尽量减少缓存未命中次数。换句话说，对于每一次缓存未命中，我们希望尽可能缩小搜索空间。

思想实验：二分查找 vs 线性查找

假设有一个排好序的 u64 数组，要查找一个目标 u64。

二分查找时，每次缓存未命中把搜索空间缩小一半。

线性查找时，每次缓存未命中排除 cache_line_size / item_size 个元素，即 64 / 8 = 8 个。

所以盈亏平衡点大约是 16 个元素：此时二分查找和线性查找代价相同，都需要两次缓存未命中才能找到目标。

但有两个附加因素：1. CPU 预取器可能自行取入后续缓存行，这让线性查找更有优势；2. 线性查找更简单，能让 CPU 流水线获得更大的并行度。所以实际的盈亏平衡点通常更高。

这对 B 树意味着什么？

在 B 树中，这决定了节点大小[4]。如果把每个节点控制在约 16–32 个元素，就始终可以使用线性查找，从而为 SIMD 等优化创造条件（见后文）。

如果键是 String 呢？ String 不一样：它的字节存在堆上，而不是内联在节点里。这彻底改变了等式。一次缓存未命中不再能取到 8 个键；每加载一个键都会产生自己的缓存未命中。所以对 String 来说，几乎总是应该用二分查找。

bbtree 怎么做？ 堆上的键非常常见，所以 bbtree 必须处理好。bbtree 引入了 inline_keys，这是数据库领域用了几十年的思路[5,6]，类似 German strings[7] 和 Arrow 的 StringView[8]。

使用固定大小的内联键后，我们又能在一次缓存未命中中加载 8 个（甚至更多）键。只有当比较打平时，才需要加载完整键。

如果键有很长的公共前缀呢？ 很多键，比如 URL 和路径，都有很长的前缀。如果只取前 8 字节作为内联键，可能什么都比较不出来。bbtree 用 prefix_keys 解决这个问题：一个节点中所有键的公共前缀[9]。prefix_keys 的巧妙之处在于，节点不必存储它们。节点中的每个键都排在父节点中该节点两侧的两个分隔键之间。因此，如果这两个分隔键的前 20 字节相同，该节点中的每个键也都以这相同的 20 字节开头。

所以每个节点只存储前缀的长度，并保留每个键紧随其后的窗口，这让内联键有效得多。

这如何应用到其他键类型？又如何与 Rust 的类型系统配合？

显然 String 和 Vec<u8> 能从这种优化中受益。但 u64、u128 这样的整数也可以；只需注意字节序：按大端存储时，它们的字节序与数值序一致。

对于其他键类型，比如结构体中的复合键，用户可以实现 InlineKey trait；实现后，我们会在所有能用的地方使用内联键。

pub trait InlineKey: Ord {
    /// How many bytes of each inline key the nodes keep: 2, 4 or 8.
    const WIDTH: InlineWidth = InlineWidth::Eight;

    /// Bytes `offset..offset + 8` of the key's encoding, big-endian,
    /// zero past its end, which orders as the keys do.
    fn inline_key_at(&self, offset: usize) -> InlineWord;
}

// A compound key, ordered by customer, then order: its encoding is
// both fields' bytes, one after the other.
#[derive(PartialEq, Eq, PartialOrd, Ord)]
struct OrderKey {
    customer: u32,
    order: u32,
}

impl InlineKey for OrderKey {
    fn inline_key_at(&self, offset: usize) -> InlineWord {
        let mut bytes = [0; 16];
        bytes[..4].copy_from_slice(&self.customer.to_be_bytes());
        bytes[4..8].copy_from_slice(&self.order.to_be_bytes());
        let start = offset.min(8);
        u64::from_be_bytes(bytes[start..start + 8].try_into().unwrap())
    }
}

let orders: BBTreeMap<OrderKey, u64, _> =
    BBTreeMap::with_strategy(WithInlineKey);

最棘手的是 Rust 的类型系统。如果要求每种键类型都实现 InlineKey，bbtree 就无法直接替换 std 的 BTreeMap/BTreeSet。Nightly Rust 的 specialization[10] 正好能解决这个问题。在 stable Rust 上，我们手动为常见类型做特化：u64、i64、u128、i128、String、str、&str、Vec<u8>、&[u8]、Box<str>、Box<[u8]>、[u8; 16]、[u8; 20]、[u8; 32]。这样内置类型无需额外工作就得到优化，用户也可以为自己的类型实现该 trait，获得完整收益。

附加：用 Rust 异步状态机实现批量模式

到目前为止，我们关注的是最大化每次缓存未命中的价值：把尽可能多的信息塞进一条缓存行。

还有一种更高级的优化：隐藏缓存未命中的代价。

隐藏延迟最简单的方法是软件预取：处理一个键时，预取下一个。这通常效果不错，但对 B 树还不够。

因为 B 树的内存访问本质上是串联的：在搜索完当前节点之前，你不知道下一个要取哪个节点。

但 B 树经常以批量方式读取或构建，这让我们可以利用 Rust 的异步状态机玩一个把戏。批量就是一次调用传入多个键，例如 BBTreeMap 的 get_many_copied 和 insert_many：输入一个键数组，输出一个答案数组。

高层思路很简单：在 Rust 中，我们常把一次 IO 操作当作 Future 并 await 它。在 bbtree 中，我们把一次缓存未命中当作 Future，也同样 await 它。数据库研究界多年来一直在手工或借助协程这样交错执行查找[11]。

代码大致如下（都在单线程中运行）：

fn get_many<const N: usize>(&self, keys: [&K; N]) -> [Option<V>; N] {
    let lanes = keys.map(|key| self.search(key));
    block_on(join_all(lanes))
}

search 大致如下：

async fn search(&self, key: &K) -> Option<V> {
    let mut node = self.root();
    while node.is_internal() {
        let edge = node.search(key);
        node = node.child(edge);
        prefetch(node.header()).await;
    }
    node.get(key)
}

但必须非常小心：

  1. 一次缓存未命中花费 100 ns，所以 Future 必须尽可能轻量。这意味着不能用 tokio 或任何通用异步运行时，因为它们的开销已经高于一次缓存未命中。bbtree 用一个极小的自有 executor 轮询各个 lane：不分配内存，没有运行时。
  2. Rust 中的每个 async 函数都是编译期生成的状态机。我们希望这个状态机尽可能小，这样状态切换才便宜。
  3. 无法知道一条缓存行是否已经在缓存中，所以只能猜。在 bbtree 中这并不难：一旦叶子节点超出 L2 缓存，访问叶子几乎总是缓存未命中；更小的树则逐个查找键。
Next, 2 of 32Minimize instructions→

总的来说，最小化指令数意味着降低 CPU 时间，这包括两件事：1. 减少指令数量；2. 减少分支。

一次分支预测失败大约花费 20 个周期（相当于 20 条指令的时间），约为一次缓存未命中的 10%。

再次比较二分查找与线性查找

有了内联键，搜索一个节点就变成搜索一个小整数数组：整数和 UUID 每个键 2 字节，字符串 4 到 8 字节。现在比较一下在 32 个键的节点上，两种查找的指令和分支：

  1. 二分查找：大约 5 步，每步一次比较和一次分支，CPU 通常有一半概率猜错。无分支二分查找[12]避免了猜测，但每一步都要等待前一步完成。
  2. 线性查找去掉提前退出后，就变成一次计数：把目标与每个键比较，数出比目标小的键有多少个；这个数量就是应该走的子节点编号。它做的比较更多，但没有分支，也不互相等待，非常适合 CPU 流水线。

bbtree 如何查找？

借助 SIMD，搜索一个节点只需要少量指令[13]。一条 AVX-512 指令可以同时把目标与 32 个两字节键比较；结果是一个 32 位掩码，每个键对应一位，掩码中 1 的个数（popcount）就是答案：

fn child_index(inline_keys: &[u16; 32], target: u16) -> usize {
    let keys = _mm512_loadu_epi16(inline_keys.as_ptr().cast());
    let smaller =
        _mm512_cmplt_epu16_mask(keys, _mm512_set1_epi16(target as i16));
    smaller.count_ones() as usize
}

这个函数只有三步，全部无分支，非常快：

  1. _mm512_loadu_epi16 把内联键加载到 SIMD 寄存器。
  2. _mm512_cmplt_epu16_mask 将它们与目标比较，返回一个掩码，每个比目标小的键对应一位，按键顺序排列（例如 1111100000000000）。
  3. smaller.count_ones() 统计掩码中 1 的个数，也就是应该走的子节点索引。x86 用一条 popcnt 指令完成。

我们也为 ARM 的 NEON 实现了同样的查找，所以 Apple Silicon 和 AWS Graviton 也能用。在 x86 上，AVX-512 需要 -C target-cpu=native（Rust 1.89 或更高版本）。

编译器不是你的朋友

我们常听到“写简单的代码，让编译器去优化”。极端例子是 FastLanes[14]，它的标量代码会被编译器自动向量化（生成 SIMD 代码）。

但在这里，编译器不是你的朋友。一个节点只有少量键，最多几十个，而且数量通常不是 2 的幂。编译器往往认为不值得向量化，有时也无法证明安全，所以我们手写 SIMD，并非常小心地处理边界情况。

在 M1 Pro 上，编译器生成的计数会把每次比较的结果扩展到 64 位，再逐个相加。我们用 NEON 手写了计数，其他什么都没改：同样的树、同样的节点、同样的缓存行。在 1000 万条目的映射中查找一个 u64 键，指令数从 1,678 降到 407，耗时从 390 ns 降到 174 ns[15]。

向量化不是唯一的问题：有时编译器因为不了解负载而生成糟糕的代码。例如比较两个 &[u8] 时，Rust 会调用 memcmp，这是一个不会被内联的函数调用。但在 bbtree 中，我们知道键通常很短，所以不调用 memcmp，而是把字节当作整数加载并比较。Arrow 对 StringView 也这么做[8,16]。

Next, 3 of 33Minimize cache coherence traffic→

当一个核心写入其他核心持有的缓存行时，就会产生缓存一致性流量。为了确保每个核心看到一致的内存视图，CPU 缓存实现了缓存一致性协议[17]。从很高层面说，对一个缓存行的写入会使其他核心中该行的所有副本失效。

这带来两个问题：1. 更多缓存未命中；2. 更重要的是，它给 B 树的并发能力设了上限。

在现代硬件上，一条被争用的缓存行最多支持约 1000 万次操作/秒。所以如果只是给 B 树加一把 Mutex，最多只能达到 1000 万 op/s；而 bbtree 在 96 线程下能达到 1.8 亿 op/s。

注意，RwLock 也没用：即使读锁也必须递增锁的读者计数，而这是一次对该缓存行的写入。

bbtree 怎么解决？

关键思想是版本锁[18,19]。每个节点带一个版本号：读者读版本号、读节点、再读版本号。如果版本号没变，读到的内容就是一致的；否则重试。

这允许非常高的并发，因为读取完全不产生写流量。

但有两件事需要小心。

问题 1：不能再把 &V 交给用户

用户持有引用期间，值可能改变甚至被释放，所以这样用是不安全的。

也不能返回 V 的克隆，因为 V 可能没有实现 Clone。

这里我们用了类似 Bf-Tree 的技巧[20]：只有内部节点是乐观的，叶子节点不是。这可行是因为：(1) 争用通常发生在内部节点；(2) 值只存储在叶子节点；(3) 在一次查找路径上，叶子节点只占 20%（假设树有 5 层）。对于 Copy 类型的值，get_copied 更进一步：它也乐观地读取叶子，把值复制出来，然后像 seqlock 一样检查版本号。

问题 2：内存回收

第二个问题更微妙：如果一个线程正在读某个节点，另一个线程把它释放了，读者可能触发段错误。

常见的解决方案是基于 epoch 的内存回收[21]，例如 crossbeam-epoch。

但这样一来，要么把 epoch 暴露给用户，丑陋且容易出错；要么每次访问都 pin 一个 epoch（很多库这么做），代价很高：每次访问都是一次全局读加一次私有写。

在 bbtree 中，我们换了一种做法：只要映射还活着，被释放的节点就永远不会还给分配器。映射把它留在空闲链表上，等需要下一个节点时复用。节点在这两步中都保留版本号：释放时递增版本号，复用时再递增一次，而版本号只增不减。所以迟到的读者读到的仍然是一个节点，而不是任意内存；它发现版本号比之前看到的更高，于是重试，不会发生段错误。

结果

bbtree 的并发能力非常强：核心数扩展到 96 时，get 吞吐量增长 83–90 倍，达到线性扩展的 86–94%。在这个线程数下，bbtree 甚至比哈希表 DashMap 还快。

如何保证正确性？

性能优化很容易：只要让 Claude 或 Codex 在某个负载上把代码提速 10 倍就行。速度是可测量的，LLM 可以不知疲倦地迭代。

但要确保代码正确很难。正确性是隐含的：你永远无法在 prompt 里列全所有“不要”，永远无法写出足够多的测试来证明代码正确，也永远无法枚举所有希望成立的性质。

bbtree 用三道防线来逼近正确性。

第一道防线：人。 Xiangpeng 是 bbtree 背后真实的人，也是守卫代码正确性的第一线。所有代码都由 LLM 编写，但每一个设计决策都由 Xiangpeng 把控，他也对代码负责。

他的博士生涯写了许许多多 B 树，其中一棵在微软生产环境中运行（Bf-Tree[20]）。选择 bbtree，意味着把这份注意力交给 Xiangpeng。

Next, 2 of 3Guard 2: LLMs→

第二道防线：LLM。 没有人能比 LLM 写出更好的代码。所有实现都由 LLM 编写，并由来自不同厂商的 LLM 交叉检查。

Next, 3 of 3Guard 3: fuzzing, verification, DSTs→

第三道防线：传统工程手段。 传统方法在这里依然适用：

  1. 模糊测试：在 bbtree 和 std 的 BTreeMap 上并排运行随机操作，检查每个答案是否一致，并在每次操作后检查整棵树的不变量：8 个 target，每周以及每次发布前运行（CI）。
  2. 形式化验证：用 Verus[22] 证明代码的关键性质，例如内联键的排序与键本身一致：证明代码，在每个 PR 上检查（CI）。
  3. 确定性模拟测试（DST）：用 Shuttle[23] 和 ffs[24] 以确定、有原则的方式测试并发行为。Shuttle 在每个 PR 上对每个测试运行数千种线程调度（CI）；ffs 由其作者运行，发现了 Shuttle 漏掉的一个竞态（issue #9），现已修复并测试。
